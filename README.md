# 食堂饭卡管理系统
（《教育机器人》课程作业，属Vibe Coding产物。。）
配套 **KL9007U UHF RFID 读卡器**（`UHFReader18` 开发包）的单机版食堂饭卡管理系统，
一台收银电脑即可运行，无需服务器、无需联网。

核心功能：**发卡、消费、充值、查询**；扩展功能：**挂失/解挂、注销/退卡、操作员登录、报表导出**。

---

## 一、快速开始

```
1. 双击 build.bat          编译（只需做一次）
2. 双击 run.bat            启动程序
3. 用 admin / admin123 登录
```

登录后程序会**自动连接读卡器**，连上了状态栏会显示型号和固件版本号。
没插读卡器也不影响使用，随时可以点右上角的「连接读卡器」重试。

首次登录后请立刻到左侧「操作员」页面修改 `admin` 的密码。

> 没有读卡器也能用：每个功能页面底部都有「手动输入 EPC」的输入框，
> 敲入卡号即可模拟刷卡，方便先熟悉流程或做演示。

## 二、界面与操作

左侧六个功能页面：

| 页面 | 用途 |
|---|---|
| **消费** | 刷卡 → 输入金额（或点常用金额）→ 回车扣款 |
| **充值** | 刷卡 → 输入充值金额 → 确认 |
| **发卡** | 刷一张空白卡 → 填姓名/工号/部门 → 确认发卡 |
| **查询** | 查卡片档案与余额；查交易流水；导出 CSV 报表 |
| **卡片管理** | 挂失、解挂、注销退卡 |
| **操作员** | 新建/删除操作员，修改登录密码 |

### 刷卡流程

1. 持卡人把卡靠近读卡器（读卡距离视卡型和功率而定，一般几厘米到几十厘米）；
2. 界面上「当前卡片」区域立刻显示卡号、姓名和余额；
3. 操作员输入金额，按回车或点按钮完成交易。

卡一直放在读卡器上**不会重复扣款** —— 同一张卡在短时间内只会上报一次，
需要把卡拿开再靠近才会再次触发。

### 发卡

拿一张空白 RFID 卡（未登记过的），刷一下，填写持卡人信息，可选地存入初始金额，
点「确认发卡」即可。系统会自动分配一个卡号（从 10001 开始）。

已经登记过的卡不能重复发卡；如果这张卡要换人用，先到「卡片管理」注销它，
再回「发卡」把它当成一张空白卡重新登记（会分配一个新的卡号）。

### 挂失 / 解挂 / 注销

- **挂失**：卡片丢失时使用。挂失后不能消费和充值，**余额保留**，找回来后可以解挂。
- **注销退卡**：员工离职时使用。系统把卡内余额结清并记一笔「退卡退款」流水，
  同时提示操作员把现金退还给持卡人。

  注销会把这张卡的档案**从本地删除**，它立刻变回一张空白卡，可以直接发给下一个人。
  已经发生的交易流水**不会丢** —— 卡号和持卡人在记账那一刻就作为快照存进了流水里，
  所以即使卡片换人甚至注销，翻查历史照样看得到当时是谁的卡。

### 查询与报表

- **卡片查询**：按卡号/姓名/工号/EPC 搜索，点某一行即可看到该卡的全部流水；
  顶部还会显示卡片总数、各状态数量和在用卡余额合计。
- **交易流水 / 报表**：按日期区间、类型、关键字筛选。日期前的方框**取消勾选**即为「不限日期」。
  点「导出 CSV 报表」会生成一个带汇总行的 CSV 文件，
  用 UTF-8 带 BOM 编码写出，Excel 双击打开中文不会乱码。

## 三、读卡器连接

| 项目 | 值 |
|---|---|
| 型号 | KL9007U / UHFReader18 |
| 协议 | EPC C1-G2（ISO18000-6C） |
| 波特率 | **57600** |
| 读写器地址 | **FF** |
| 工作模式 | **应用模式**（命令应答式） |

程序用 57600 波特率自动扫描串口，连上后会显示读回的型号和固件版本号，
这就是"真的连上了"的证据。登录进主界面时会自动连一次；
连不上也不会弹窗打扰，点右上角「连接读卡器」可随时手动重试。

**连不上时依次检查：**

1. 读卡器是否通电、USB 线是否插紧；设备管理器里应能看到一个 USB 转串口（CP210x）的 COM 口；
2. 有没有别的程序（尤其是开发包自带的官方 Demo）正占着这个串口 —— 串口是独占的；
3. 读卡器的工作模式是否为「应用模式」。如果是「主动模式」，盘点命令不会有返回，
   请先用官方 Demo 把它切回应用模式。

**重要**：读卡器未连接时程序照常可用，查询、报表、手动输入 EPC 都不受影响。

## 四、数据与备份

所有数据都在一个 SQLite 文件里：

```
bin\data\mealcard.db
```

- **备份**：关掉程序，直接复制这个文件即可。恢复时把它拷回去覆盖。
- **换位置**：用 `run.bat --db=D:\某个目录\mealcard.db` 指定，适合把数据放在共享盘或移动硬盘。
- 这个文件包含了全部卡片、余额和流水，**请定期备份**，丢了无法恢复。

### 对账

系统保证「卡片余额」与「流水累加」永远一致，任何时候都可以核对：

```
某张卡的余额 = Σ开卡 + Σ充值 − Σ消费 − Σ退卡退款
```

任何一次余额变动都在同一个数据库事务里同时写入流水，不会出现扣了钱没记账、
或记了账没扣钱的情况。

## 五、常见问题

**Q：金额会不会出现 0.1 + 0.2 = 0.30000000000000004 这种误差？**
不会。系统内部一律以整数「分」存储和运算，只有显示时才格式化成 `12.50`。

**Q：能同时开两个窗口吗？**
不能，程序会自动阻止。同一台机器同时开两个会让操作员看到互相矛盾的余额。

**Q：忘记管理员密码了怎么办？**
用另一个管理员账号登录后重置。如果所有管理员密码都丢了，
把 `mealcard.db` 里 `operators` 表清空（或删除整个数据库文件）后重新启动，
程序会重新创建 `admin / admin123` —— 但卡片和流水数据会一并丢失，请务必先备份。

**Q：能支持多个收银台吗？**
本系统是单机版。多个收银台同时用同一个数据库文件会导致余额竞争，不建议。

## 六、开发者说明

### 编译

本机没有 .NET SDK、没有 NuGet，因此直接用 .NET Framework 自带的 `csc.exe` 编译：

```
build.bat            编译（release，输出 bin\MealCardSystem.exe）
build.bat debug      带调试符号编译
build.bat selftest   编译并运行业务逻辑自检（不需要硬件）
build.bat uismoke    编译并运行界面冒烟测试（不需要硬件）
build.bat check      跑上面两个测试
build.bat clean      清理编译产物（不动 data\ 目录）
```

### 两条硬约束

1. **必须 `/platform:x86`** —— `UHFReader18CSharp.dll` 通过 P/Invoke 调用 32 位的原生
   `Basic.dll`，编译成 64 位会在运行时抛 `BadImageFormatException`。
2. **源码只能用 C# 5 语法** —— 本机的 `csc.exe`（v4.0.30319）只支持到 C# 5。
   不可使用字符串插值 `$""`、`nameof`、表达式体成员、`?.`、自动属性初始化器、
   `using static`、元组、`out var`。LINQ / lambda / 泛型 / 可选参数 / `async` 可用。

### 不依赖第三方库

- **SQLite**：直接 P/Invoke 系统自带的 `winsqlite3.dll`（Windows 10/11 内置，
  导出完整的标准 SQLite C API），全部封装在 `src\Data\Sqlite.cs` 一个文件里。
  将来若要换成官方 `System.Data.SQLite`，只需改这一个文件。
- **读卡器**：直接引用开发包里的 `UHFReader18CSharp.dll`（纯托管程序集），
  由 `src\Reader\RfidReader.cs` 封装，上层代码不碰 SDK 细节。

### 目录结构

```
MealCardSystem\
├── build.bat / run.bat          一键编译、启动
├── lib\                         读卡器 DLL（从开发包 bin\Debug 复制）
├── bin\                         编译产物 + data\mealcard.db
├── src\
│   ├── Program.cs               入口：开库 → 登录 → 主界面
│   ├── Model\                   Card / Transaction / Operator
│   ├── Data\                    Sqlite.cs（P/Invoke 封装）+ 各仓储
│   ├── Reader\RfidReader.cs     读卡器连接、盘点、防重复刷卡
│   ├── Service\                 发卡、消费充值（事务）、报表
│   ├── UI\                      全部界面（纯代码构建，无设计器）
│   └── Util\                    金额换算、十六进制、CSV
└── tests\SelfTest.cs            业务逻辑自检
```

### 自检覆盖范围

`build.bat check` 会跑两套不依赖硬件的测试：

- **业务自检**（119 项）：登录鉴权、发卡、充值、消费、
  余额与流水一致性、失败操作不留痕迹、挂失后消费被拒、注销退卡、
  注销后卡片档案被删除且流水快照仍然完整、换人重发后老流水不被覆盖、
  金额解析边界、EPC 规范化，以及**旧版数据库的升级**（老库的流水表没有快照列，
  注销也只是标记状态，升级时要回填快照并清掉遗留的已注销记录）。
- **界面冒烟测试**：在临时数据库上走一遍完整业务，再把登录窗口和六个功能面板
  全部构造、切换、渲染一遍，用于捕捉界面代码里的空引用和越界。
  另外专门验证两条容易被忽略的界面规则：**切走再切回后余额必须刷新为最新值**，
  以及**注销后的卡必须显示为未登记的空白卡**。
  最后用各面板真实的提示文案把**提示框排版**过一遍：每一层控件都要落在
  父容器的客户区里（跑出去的部分会被静默裁掉），字号也必须确实比
  系统 MessageBox 的约 9pt 大。

### 提示框为什么是自绘的

系统 `MessageBox` 固定使用约 9pt 的消息框字体，而且没有提供任何修改接口。
收银时「本次消费 / 卡内余额」这两个数字要一眼看清，所以 `UiKit.Info / Warn /
Error / Confirm` 改为弹出工程内自绘的 `MessageDialog`（四个方法的签名没变）。
排版沿用各面板既有的文案写法：首行是标题，空行分段，形如「标签：值」的行
拆成两列、值加粗放大（15pt），正文 12pt。字体逐次创建、随窗体一起释放——
这个框每笔交易都要弹一次，漏掉 GDI 句柄迟早会把进程耗尽。
